# アーキテクチャ

## 大前提: ロジックはサーバに1本、起動はローカルで完結

**ビジネスロジックは Rails にだけ置き、GraphQL で4クライアントへ供給します。**
同時に、**起動と最初の1タップは端末だけで完結**させます。

この2つは一見矛盾しますが、順序で両立させています（後述の遅延登録）。

```
┌──────────────────────────────────────────┐
│  nikkake_api (Rails 8)                   │
│    lib/domain/     ActiveRecord を知らない純粋関数
│    app/services/   画面1枚ぶんを組み立てる
│    app/graphql/    受け口。ロジックは書かない
└───────────────────┬──────────────────────┘
                    │ GraphQL（画面 = クエリ1本）
   ┌────────────┬───┴────────┬────────────┐
   │            │            │            │
  Web    React Native     Flutter        KMP
```

### なぜサーバへ寄せたか

移行前は同じアプリの実装が3つあり、同期ロジックだけで3言語543行が別々に書かれていました。
仕様を変えると3か所直す必要があり、片方だけ直すとサイレントにデータがズレます。

実際に起きていた例:

- KMP だけタイムスタンプを文字列比較していて `.500Z` が `Z` より前になっていた
- 「前回: 50×10」の文言が Ruby では `50.0×10`、TypeScript では `50×10` になっていた
- プリセット種目の固定UUIDが4か所に手書きコピーされ、人力ルールで守られていた

いずれも「同じ計算を複数の言語に書いた」ことが原因です。
いまは [packages/contract](../packages/contract) を唯一の正とし、
[CONTRACT.md](CONTRACT.md) の仕組みで機械的に検査しています。

## 遅延登録（lazy registration）

匿名アカウントをサーバ発行にすると、素直に作れば
**新規インストール直後に圏外だとアプリが1歩も動きません。**
[FEATURES.md](FEATURES.md) の絶対条件「起動直後に1タップで始められる」に反します。

そこで順序を逆にしています。

```
初回起動
  1. 端末でシード（プリセット種目25件 +「いつものルーティン」）
  2. ホームを描画            ← ここまでネットワークゼロ
  3. 以降バックグラウンドで
       createAnonymousAccount（withStarterRoutine: false）
       importSnapshot（端末のデータを丸ごと預ける）
       成功 → サーバ計算モードへ切り替え
       失敗 → 何もせず、次の起動で再試行
```

実装では待つ処理と待たない処理を関数として分けています
（`nikkake_react_native/src/lib/bootstrap.ts`）。

| 関数 | 待つか | 内容 |
|---|---|---|
| `prepareLocalData()` | **必ず待つ** | シードのみ。ネットワークを使わないので必ず終わる |
| `registerInBackground()` | **絶対に待たない** | 登録と預け入れ。失敗しても例外を投げない |

### 切り替えは実行時に起きる

「サーバモードかどうか」はビルド時（`EXPO_PUBLIC_BACKEND`）に決まりますが、
**「サーバを使ってよいか」は実行時に変わります**。
登録が終わるまではローカル実装で動き、終わった瞬間に切り替わります
（`src/lib/session.ts` / `repository.ts`）。

このため、データ取得の実装をモジュール読み込み時に固定してはいけません。
固定するとローカルのまま戻らなくなります。

### 切り替えの隙間

登録が終わる前でもユーザーは操作できます（それがこの設計の目的です）。
そのため「1回目の預け入れ」と「サーバ切り替え」のあいだに書かれた記録は、
どちらにも属さないまま取り残される可能性があります。

切り替えた直後にもう一度預け直して塞いでいます。
ID は端末生成で `ON CONFLICT DO NOTHING` に吸収されるため、再送は安全です。

### クライアントに残る計算

未登録のあいだは端末が集計する必要があるため、純粋関数を完全にはゼロにできません。
これは「初回だけネット必須」を受け入れない限り避けられない構造的な妥協です。

| 残すもの | 理由 |
|---|---|
| ローカル実装一式（RN） | 未登録モード用。`repository.local.ts` |
| 日付文字列の生成 | `log_date` は端末が決める（後述のタイムゾーン） |
| `formatDuration` / `formatWeight` | 毎秒描画・入力中表示。往復できない |

ローカル実装が返す型は、サーバ実装が返す型と**同一**です。
`repository.ts` の `Repository` インターフェースが両方を縛っているので、
片方だけ形が変わればコンパイルが落ちます。

## GraphQL は「画面 = クエリ1本」

汎用的な `routines { logs { ... } }` を返すと、結局4実装に集計ロジックが戻ります。
集計済みのビュー型を返します。

| 画面 | クエリ | サーバ側 |
|---|---|---|
| ホーム | `home(today:, timeZone:)` | `HomeViewBuilder` |
| ワークアウト | `workoutSession(routineId:)` | `WorkoutSessionBuilder` |
| 進捗 | `progress(today:, timeZone:, rangeDays:)` | `ProgressViewBuilder` |

「今日やる／今日は予定なし／完了」の区分も、`frequencyLabel`（「毎日」「3日ごと」）も、
`previousLabel`（「前回: 50×10 / 50×9」）もサーバが決めます。
[FEATURES.md](FEATURES.md) が「文言まで一致」を要求しており、
サーバに寄せるとパリティ維持コストがそのぶん消えます。

## タイムゾーン

移行前は端末の `new Date()` で完結しており、原理的に間違えようがありませんでした。
サーバを挟むと「クライアントが送る日付」「リクエストのTZ」「`users.time_zone`」
「サーバの `Time.zone`」の4つがずれる余地が生まれます。

**ストリークが1日ずれるのはこの習慣化アプリで最も致命的なバグ**なので、設計で潰しています。

### 原則1: サーバは「今日」を計算しない

日本の朝8時は UTC では前日23時です。サーバが `Date.today` を使えば即座に1日ずれます。

クライアントが `today` と `timeZone` を必ず送り、サーバは受け取った値だけを使います。
`nikkake_api/spec/architecture_spec.rb` が機械的に検査しています。

### 原則2: `log_date` はクライアントが決める

記録時に端末のローカル日付で確定させ、そのまま保存します。
サーバは検証のみ（未来日でないか、極端に古くないか）で、UTC から導出することはしません。

### 原則3: 記録時のタイムゾーンを保存する

```
routine_logs.client_time_zone            "Asia/Tokyo"
routine_logs.client_utc_offset_minutes   540
```

事故が起きたときに検証・救済できる余地を残すためです。
これが無いと、日付がずれた記録を後から直せません。

### 原則4: `users.time_zone` は判定に使わない

バッチ処理にはフォールバックが要りますが、判定には常にリクエストの値を優先します。
海外旅行中に `users.time_zone` を見ると、その場の「今日」とずれます。

### 原則5: 既存の猶予がTZ耐性になっている

ストリーク判定は「最終実施日が今日か昨日なら継続」です。
これが **±1日のTZズレを構造的に吸収**します。
UX のための猶予として入れたものが、そのままTZ耐性として効いています。
うっかり厳格化しないでください。

DST も問題ありません。日数差の計算が丸めを使っており、23時間・25時間の日を吸収します。

### 残るリスク

**日付変更線を跨ぐ西→東の移動**（ハワイ→日本など）では1日が消え、ストリークが切れます。
頻度が低いので割り切りますが、原則3で記録時のTZを保存しているので後から救済できます。

**0時区切りを維持したことによる残存問題**: 深夜1時に運動した人は「その日」の記録になり、
前日はサボり判定になります。仕様として0時区切りを選んだので現状維持です。

## オフラインで何ができるか

| 操作 | オフライン |
|---|---|
| 起動・閲覧 | できる（キャッシュとローカル） |
| ワークアウトの記録 | **できる**（キューに積んで復帰時に送る） |
| ルーティンの作成・編集 | **できない**（保存ボタンを無効化する） |

ルーティンの作成をオフライン不可にしたのは明確な機能後退です。
圏外で作れると、サーバの採番や検証を通っていないルーティンに対して記録が積まれ、
整合を取る手段が無くなるためです。

### 記録のキュー

`packages/api-client/src/queue.ts`。

- **直列に送る。** 失敗したら `break` して順序を守る
- 永続エラー（VALIDATION / NOT_FOUND）は dead キューへ。設定画面で手動対応
- ネットワーク・5xx は指数バックオフ（1s, 2s, 4s … 最大5分）
- 起動条件: フォアグラウンド復帰 / オンライン復帰 / 記録直後 / 30秒タイマー

### 冪等性は2段構え

1. **クライアント生成 UUID を主キーにする**（主機構）。再送しても同じIDなので二重登録されない
2. **`mutation_receipts` による応答リプレイ**（補助）。「サーバは処理したが応答が失われた」
   ケースで同じ応答を返す。`(user_id, key)` のユニークインデックスが並行再送を止める

## 認証

gem は bcrypt のみで、Rails 標準の機構を使っています。

Devise も Rodauth も「アカウント = メールアドレス」前提で、匿名先行と噛み合いません
（Rodauth は `accounts.email` が NOT NULL UNIQUE 必須）。
ダミーメールを詰めると、偽データが制約・メール送信・昇格処理の全てに漏れ出します。

```ruby
# app/models/api_token.rb — 生トークンは発行時にしか存在しない
def self.issue!(user, device_label: nil)
  raw = SecureRandom.urlsafe_base64(32)   # 端末IDから導出しない
  [ create!(user: user, device_label: device_label, token_digest: digest(raw)), raw ]
end
```

**端末IDから導出してはいけません。** 端末IDは秘密ではなく、リセットされ、Web には存在しません。

メール登録への昇格（`attachEmailPassword`）は `user.id` が変わらないので、
**データ移行が一切発生しません**。

### 認可

`Routine.find(id)` を書ける状態にしないことが主防御です。必ず `current_user` から辿ります。
これも `spec/architecture_spec.rb` が検査しています。

存在しないIDと他人のIDは同じ `NOT_FOUND` にします（IDの存在有無を漏らさないため）。

## 実装ごとの層の対応

| 層 | Rails | Web | React Native | Flutter / KMP |
|---|---|---|---|---|
| ドメイン | `lib/domain/` | — | `src/lib/stats.ts`, `utils.ts`（未登録モード用） | `domain/` |
| 組み立て | `app/services/` | — | `repository.local.ts` | `data/Repository` |
| API | `app/graphql/` | `packages/api-client` | `repository.server.ts` | 未接続 |
| 画面 | — | `src/routes/` | `src/app/` | `ui/` |
| 状態管理 | — | TanStack Query | Zustand + TanStack Query | Provider / Compose state |

### 状態管理を統一していない理由

各プラットフォームの標準的なやり方に寄せています。無理に同じパターンへ揃えると
どの実装から見ても不自然になり、その言語の開発者が読みにくくなるためです。
**揃えているのは層の切り方とデータの意味**であって、フレームワークの使い方ではありません。

## グラフ描画ライブラリを使っていない理由

進捗画面のグラフとカレンダーは、矩形の高さと色だけで描いています。

- 4クライアントで同じ見た目を再現しやすい
- E2E で確実に描画され、テストが安定する
- 依存が増えない

表現力が要る段階になったら差し替えを検討します。

## この移行で失われたもの

正直に残します。

1. **オフラインでのルーティン作成・編集ができなくなった**
2. **サーバ障害＝全クライアント停止。** 移行前は Supabase が落ちても3実装とも無傷だった
3. **画面操作にネットワーク待ちが発生しうる。** 新端末やキャッシュ破棄後は確実に遅くなる
4. **運用コストが発生する**（Rails のホスティング費。DB は移行前から使っている）
5. **メンテ対象が3→5に増えた**
6. **CI が重くなった。** PostgreSQL と Rails を立てないと E2E が走らない
7. **プライバシー面の変化。** 移行前は「端末にしか無い」が既定だった。
   移行後は登録後に全記録がサーバへ送られる
