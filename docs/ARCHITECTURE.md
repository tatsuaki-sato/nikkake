# アーキテクチャ

## 大前提: ローカルファースト

**端末のローカルストレージが唯一の真実の源(source of truth)です。**

画面が読むデータも書くデータも、すべてローカルストレージに対して行われます。
ネットワークは一切介在しません。その結果として:

- サインインしなくても全機能が使える
- 圏外（ジムの地下など）でも完全に動く
- 画面操作にネットワーク待ちが発生しない

Supabase は「サインインしたユーザーのバックアップ兼マルチデバイス同期先」であって、
アプリの動作に必須の依存ではありません。Supabase の初期化に失敗しても、
3実装すべてがローカルモードで通常どおり起動します。

```
┌─────────────┐
│   画面      │  参照も更新もローカルのみ。同期の成否は待たない
└──────┬──────┘
       │
┌──────▼──────┐
│ Repository  │  ドメインAPI（ルーティン/ログ/統計）
└──────┬──────┘
       │
┌──────▼──────┐
│  LocalDb    │  JSONコレクションのCRUD＋論理削除＋差分抽出
└──────┬──────┘
       │
┌──────▼──────┐
│  Storage    │  AsyncStorage / SharedPreferences / NSUserDefaults …
└─────────────┘

       ⇅  （サインイン中のみ、バックグラウンドで）

┌─────────────┐
│ SyncService │  push → pull の順に双方向同期
└──────┬──────┘
       │
┌──────▼──────┐
│  Supabase   │
└─────────────┘
```

## 起動シーケンス

1. ローカルストレージを開く
2. `seedIfNeeded()` — 初回起動ならプリセット種目25件と「いつものルーティン」を投入
3. **ここでホーム画面を表示する**（この時点で全機能が使える）
4. 以降はUIをブロックせずに認証状態を確認し、サインイン済みなら同期を走らせる

3 と 4 の順序が重要です。認証の確認を待ってから画面を出すと、
圏外や Supabase 障害時に起動できなくなります。

## 同期の設計

### 衝突解決: last-write-wins

全エンティティが `updated_at` を持ちます。同じIDのレコードがローカルとリモートの
両方にある場合、`updated_at` が新しい方を採用します。

比較は必ず**時刻としてパースしてから**行います。文字列比較にすると小数秒の有無で
桁数が変わり、`…:00.500Z` と `…:00Z` の前後が逆転します（`'.' < 'Z'` のため）。
これは同期の取りこぼしに直結するので、3実装ともテストで守っています。

### 削除は論理削除

物理削除にすると「削除した」という事実が同期先に伝わらず、他端末から pull し直すたびに
復活してしまいます。そのため削除は `deleted_at` を立てるだけで、行自体は残します。

画面に出るのは `deleted_at IS NULL` の行だけです（`LocalDb.list()`）。
同期処理だけが削除済みも含む生データ（`LocalDb.listRaw()`）を見ます。

### 差分カーソル

`meta.lastSyncedAt` を「前回の同期を**開始**した時刻」として保存します。
完了時刻ではなく開始時刻にしているのは、同期の処理中に発生した変更を
次回の同期で取りこぼさないためです。

`meta.syncUserId` が現在のユーザーと違う場合（別アカウントでサインインし直した場合）は
カーソルを捨てて全件を取り直します。

### push が先、pull が後

同じレコードを両方が持っていた場合に、サーバ側の `updated_at` が確定してから
pull したいためです。テーブルは親→子の順（exercises → routines → routine_exercises →
routine_logs → exercise_logs）で処理し、外部キー制約を壊さないようにしています。

### サインイン時のデータ引き取り

サインインするまで、ローカルのレコードは `user_id = null` で作られます。
サインイン直後に `claimLocalRows(userId)` が全件の `user_id` を埋めるので、
それまでに作った記録もそのままクラウドへ引き継がれます。

### プリセット種目は送らない

プリセット種目はサーバ側にも同じIDで存在する共有マスタなので、push対象から除外します。
IDは全プラットフォーム共通の固定値です（[DATA_MODEL.md](DATA_MODEL.md) 参照）。

## サインアウトの意味

サインアウトしても**ローカルのデータは消しません**。
「クラウドへのバックアップをやめる」だけであって、記録を捨てる操作ではないからです。
3実装とも確認ダイアログにその旨を明示しています。

## 実装ごとの層の対応

| 層 | React Native | Flutter | KMP |
|---|---|---|---|
| ストレージ | `src/lib/storage.ts` | `lib/data/local_store.dart` | `data/PlatformStorage.kt`（expect/actual） |
| ローカルDB | `src/lib/localDb.ts` | `lib/data/local_db.dart` | `data/LocalDb.kt` |
| ドメインAPI | `src/lib/repository.ts` | `lib/data/repository.dart` | `data/Repository.kt` |
| 同期 | `src/lib/sync.ts` | `lib/data/sync_service.dart` | `data/SyncService.kt` |
| 日付・統計 | `src/lib/utils.ts`, `stats.ts` | `lib/domain/` | `domain/` |
| 状態管理 | Zustand + TanStack Query | ChangeNotifier (Provider) | Compose `mutableStateOf` |
| 画面遷移 | Expo Router | Navigator (MaterialPageRoute) | 自前の `Navigation`（sealed interface） |

### 状態管理を統一していない理由

各プラットフォームの標準的なやり方に寄せています。無理に同じパターンへ揃えると
どの実装から見ても不自然になり、その言語の開発者が読みにくくなるためです。
**揃えているのは層の切り方とデータの意味**であって、フレームワークの使い方ではありません。

## グラフ描画ライブラリを使っていない理由

進捗画面のグラフとカレンダーは、矩形の高さと色だけで描いています。

- 3プラットフォームで同じ見た目を再現しやすい
- Web(Playwright)でも確実に描画され、E2Eが安定する
- 依存が増えない

表現力が要る段階になったら差し替えを検討します。
